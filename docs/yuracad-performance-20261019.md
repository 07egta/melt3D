# YuraCAD / Melt3D 軽量化の測定記録（2026-10-19）

CPU の距離計算、クリック時のレイ判定、多重選択の展開を軽量化した。さらに、CPU 描画の移動中のパスが誤って細密描画になっていた箇所を修正した。形状、材質、選択対象の順序を維持する回帰テストと、旧処理を同じバイナリ内で動かす比較測定を追加している。

測定では、20,000 点の距離計算は旧処理の **1.16〜2.25 倍**、100 個と 300 個の多重選択の展開はそれぞれ **2.32 倍、5.11 倍**の処理速度になった。レイ判定は場面によって異なり、パイプの例は **0.99 倍**で改善を確認できなかった。ここに載せる数値は各 CPU 処理の測定値であり、アプリ全体の FPS や Windows の操作速度を表すものではない。

## 変更した処理

### 距離が必要な箇所で材質計算を省く

[`sdf.rs`](../apps/meltcad/src/sdf.rs) の `Field::distance` とレイの前進処理から、色のグラデーション、粗さ、金属度、選択 ID の合成を省いた。`Field::sample` は従来どおりすべてを返し、`Field::ray` は表面に当たった位置で材質と選択 ID を求める。Paint は距離を変えないため、距離専用処理では形状単位の Paint 評価を省略する。

Add / Subtract / Intersect の距離式、ブレンド、境界によるスキップ、座標変換、レイの閾値・歩幅・上限は維持した。シェーダーの距離式や既存の形状キャッシュを置き換える変更は含まない。

子を持たないグループは、その場で親に合成する。平坦なシーンでは、サンプルごとに階層スタックの `Vec` を確保して push / pop する処理が不要になる。階層のあるシーンでは必要なスタックを引き続き使う。リンク先が欠けたグループを解決時に省いた場合も、実際の並びを確認してから即時合成し、後続の子を誤った親に付けない。

### 多重選択の重複確認を短くする

[`view.rs`](../apps/meltcad/src/view.rs) の `targets_all` は、選択ごとの一時配列と、増え続ける結果全体の線形探索を省いた。所属確認に `HashSet` を使い、返す配列は従来の「最初に現れた順」に保つ。グループ選択と形状選択の重複、不正なインデックス、ギズモの中心の計算も比較している。選択が 0 件または 1 件の経路は従来のままにした。

### 移動中と静止時の CPU 描画を分ける

[`easy_view.rs`](../apps/meltcad/src/easy_view.rs) では、これまで「要求の最後のパス」を「細密描画」と同じフラグで判定していた。移動中はパスが 1 つなので、粗いサイズでも細密の陰影計算をしていた。

要求が移動中かどうかをワーカーに渡し、`last`（要求の完了）と `fine`（細密描画）を分けた。移動中の 1 パスは軽い陰影で完了し、静止後の最後のパスで細密描画に戻る。実際のワーカーに移動・静止の要求を順に送り、軽い画像と細密画像がそれぞれ既存の参照レンダリングとバイト単位で一致することを確認した。この修正単独の所要時間は測定していない。

### サムネイルが別の画面に渡る不具合

[`library_ui.rs`](../apps/meltcad/src/library_ui.rs) のサムネイルは、テクスチャを `egui::Context` ごとに保存していた一方、生成要求と完成画像のキューはプロセス全体で共有していた。別の Context が完成画像を先に回収すると、元の Context に画像が届かず、共有の重複防止処理が再要求も止めていた。

ワーカーを Context の一時データに保持し、要求・完成画像・テクスチャの所属を一致させた。完成画像を用意してから別の Context に先に回収させる回帰を追加し、処理速度に依存せず取り違えを検出する。元の待機テストは修正前でも単体なら 0.04 秒で成功し、通常の生成速度不足は確認できなかった。テストの待機期限を延長する変更はしていない。

## 測定環境と比較方法

| 項目 | 条件 |
|---|---|
| 実施日 | 2026-10-19 UTC |
| 基点 | `53c487c22243c4a8c2a42720e167b7aa83015405` に本変更を適用した作業ツリー |
| OS | Linux 6.18.55、x86_64、KVM 環境 |
| CPU 表示名 | AMD EPYC 9V74 80-Core Processor |
| 実行環境の制限 | 論理 CPU 9 個を認識、cgroup の CPU 割当は 8 CPU 相当、メモリ上限 8 GiB |
| Rust | rustc 1.95.0 (`59807616e`)、LLVM 22.1.2 |
| プロファイル | `ci`: アプリ opt-level 1、依存 opt-level 2、debug-assertions 無効、overflow-checks 有効、incremental 無効 |
| 追加フラグ | `RUSTFLAGS='-C codegen-units=1'`、ビルドの並列数 2 |
| 計測の並列数 | 1 テストスレッド。3 つのベンチを順次実行 |
| 集計 | ウォームアップ 1 回の後、旧・新処理の実行順を交代して 7 回計測し、各処理の中央値を比較 |

コンパイルや別の重い検証と競合しない時間に測定した。CPU のコアやクロックは固定しておらず、共有仮想環境の変動は残る。小さな差を有意な改善とは扱わない。

旧処理は [`sdf_sampling_tests.rs`](../apps/meltcad/src/sdf_sampling_tests.rs) の `reference_sample` / `reference_ray` と、`view.rs` 内の `reference_targets` に保存してある。旧スタックの操作順や各ステップでの材質評価を残し、同じ準備済み形状を使って新処理と比較する。別々の製品版バイナリを比較した数値ではない。SDF の参照側も形状単体の距離計算は共有しており、今回変更した階層の合成順と材質評価の省略を検証するための参照実装である。

Field の準備、入力点・レイの作成、カメラ設定、画像の陰影計算、UI 表示は距離・レイの計測に含めていない。材質を返す処理は返り値全体を `black_box` に渡し、未使用の材質計算が最適化で消えないようにした。測定ごとに距離またはヒット位置のチェックサムが旧処理と完全に一致することも確認している。

## 結果

「速度比」は旧処理の時間 ÷ 新処理の時間。1 より大きいと新処理が速い。

### 20,000 点の CPU 距離計算

シーンの境界周辺に、同じシードから決定的に生成した点を置いた。時間は 20,000 点の処理全体のミリ秒。最後の列は、距離だけでなく材質も返す `sample` の新処理で、速度比の分母には使っていない。

| シーン | 実形状数 | 旧 sample（ms） | 新 distance（ms） | 距離の速度比 | 新 sample（ms） |
|---|---:|---:|---:|---:|---:|
| default | 1 | 1.560 | 0.693 | 2.25 倍 | 1.304 |
| gradient | 4 | 4.018 | 2.237 | 1.80 倍 | 3.832 |
| nested | 90 | 42.133 | 23.586 | 1.79 倍 | 41.323 |
| shapes100 | 106 | 19.903 | 13.931 | 1.43 倍 | 18.506 |
| shapes300 | 322 | 66.576 | 57.555 | 1.16 倍 | 65.537 |

`nested` は深いグループ、グラデーション、Paint、シェル、パターン、リンクを含む。`shapes100` / `shapes300` はライブラリのモデルを足して目標数以上にする既存の生成関数を使うため、実数は 106 / 322 となる。

### カメラからの 2,560 本の CPU レイ判定

64 × 40 の画面上の位置からレイを作り、表面に当たったときの材質の取得まで含めた。時間は全レイの処理時間。描画後処理や GPU のフレーム時間ではない。

| シーン | 実形状数 | 旧 ray（ms） | 新 ray（ms） | 速度比 |
|---|---:|---:|---:|---:|
| default | 1 | 2.861 | 1.589 | 1.80 倍 |
| pipe | 1 | 61.658 | 62.507 | 0.99 倍 |
| gradient | 4 | 5.344 | 3.045 | 1.75 倍 |
| shapes100 | 106 | 16.428 | 11.459 | 1.43 倍 |
| shapes300 | 322 | 57.533 | 49.272 | 1.17 倍 |

pipe は約 1.4% 遅く、この測定ではほぼ同程度だった。形状の距離計算が支配的な場合、材質評価を省く効果は小さく、ヒット時に材質を求め直す分の処理もある。すべての形状で速くなるとは主張しない。

### 多重選択の展開

各形状を個別に選択した配列を展開し、1 呼び出しあたりのマイクロ秒に換算した。各計測の繰り返し回数は `30000 / 形状数`。

| 選択形状数 | 旧処理（µs） | 新処理（µs） | 速度比 |
|---|---:|---:|---:|
| 10 | 0.234 | 0.248 | 0.94 倍 |
| 100 | 4.880 | 2.104 | 2.32 倍 |
| 300 | 31.038 | 6.069 | 5.11 倍 |
| 1,000 | 305.248 | 19.925 | 15.32 倍 |

10 個では約 14 ns 遅く、小規模での改善は確認できなかった。通常の保存データの形状上限は 512 個なので、1,000 個の行は関数の伸び方を見る負荷試験であり、通常のシーンの性能を表さない。

## 回帰テスト

この性能作業で直接実行した通常テストは、`sdf::sampling_tests` の 5 件、`easy_view::tests` の 11 件、`view::tests` の 4 件が成功した（重複を除いて 20 件）。追加した 3 つの ignored ベンチも成功した。

| 対象 | 確認内容 |
|---|---|
| 距離と材質 | 全ブレンドモード、drip の有無、nested の Paint / shell / pattern / linked、局所・世界座標のグラデーション。距離、RGB、粗さ、金属度を浮動小数点のビット単位で照合 |
| レイと選択 ID | 全ライブラリモデルで、ヒット有無、ヒット位置、材質、選択対象が旧処理と一致 |
| 階層 | 空シーン、未正規化の深さ 0〜255、リンク先欠損を省いた後の深いグループでも旧合成順を維持 |
| 不正な数値 | NaN、正負の無限大、負のゼロ、すべての形状演算。panic がなく、距離の分類とレイのヒット有無が一致 |
| 多重選択 | グループと個別形状の重複、無効なインデックス、最初に現れる順、ギズモ中心、10〜1,000 個の比較 |
| CPU 描画ワーカー | 移動要求を軽い描画で完了し、次の静止要求の最終画像が既存の細密画像とバイト単位で一致 |

警告の修正でも数値の意味を維持した。`Prepared::color_at` の `max/min` は NaN を先頭色に戻す挙動を持つため `clamp` に変更せず、局所的に理由を記載した。`face_melt_distance` の `6.2832` も `shader.wgsl` と同じ値を維持する。使われていない旧ラッパーやテスト専用関数の整理を含むが、これによるバイナリ容量やメモリの削減量は測定していない。

## 再実行

Rust 1.95.0 が利用できる環境で、リポジトリのルートから実行する。測定に使った環境では、複数の codegen unit を使う依存ビルドにリンカーの異常が出たため、上記のフラグでビルドした。

```sh
export CARGO_TARGET_DIR="$PWD/target"
export CARGO_BUILD_JOBS=2
export RUSTFLAGS='-C codegen-units=1'

cargo +1.95.0 test -p meltcad --profile ci --locked --no-run

cargo +1.95.0 test -p meltcad --profile ci --locked cpu_sampling_speed -- --ignored --nocapture --test-threads=1
cargo +1.95.0 test -p meltcad --profile ci --locked cpu_ray_speed -- --ignored --nocapture --test-threads=1
cargo +1.95.0 test -p meltcad --profile ci --locked multi_selection_speed -- --ignored --nocapture --test-threads=1
```

通常の回帰テストは次で実行できる。ignored ベンチはこのコマンドでは走らない。

```sh
cargo +1.95.0 test -p meltcad --profile ci --locked
```

公開用の性能値には release ビルドと実機での追加測定が必要となる。この記録では、release ビルドの速度、Windows 実機、Intel Arc 140V 等の GPU、アプリ全体の FPS、起動時間、EXE 容量、プロセスメモリを測定していない。また、非同期の移動・静止描画は正しさをテストしており、操作遅延の改善量を計測したものではない。
